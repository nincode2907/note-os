## 1. Objective

Upgrade noteOS Web backup/restore so that a user can safely export and restore ALL supported local note data, including:

- Active, archived and trashed notes.
- Canonical document JSON.
- Titles, tags, pin, revisions and timestamps.
- Audio recording metadata.
- Original audio bytes, including completed and recoverable interrupted recordings.

The resulting archive must be self-contained, integrity-checked, backward-compatible with existing v1 notes-only backups, and safe to import without overwriting user data.

**This is a data-durability milestone, not a new feature platform.**

## 4. Full Archive V2 format

Design one deterministic, self-contained archive using a standard, broadly readable format such as `.zip` or `.tar`.

Evaluate available libraries and browser memory behavior before selecting the implementation. Avoid new heavyweight dependencies.

Suggested logical structure:

    manifest.json
    notes.json
    recordings.json
    blobs/<recording-id>.<extension>

`notes.json` remains the authoritative canonical representation of note records.

`recordings.json` preserves recording metadata, noteId relationships, original MIME types, timing and recording statuses.

Audio blobs must preserve their original byte sequences and correct MIME/extension mapping.

The manifest should contain:

- Format identifier: `noteos.archive`
- Version: `2`
- Export timestamp
- Source platform
- Record counts
- File names
- Byte lengths
- SHA-256 checksums
- Relevant archive warnings and skipped entries, if any

Keep future schema evolution possible.

Do not introduce Audio Anchors as a feature in this pass, but ensure the archive format can preserve additional validated recording metadata without requiring a redesign.

Do not build an HTML backup viewer, AI integration, or Markdown exporter in this milestone.

## 5. Snapshot consistency

The current repositories read from IndexedDB independently.

Do not simply loop over notes and audio repositories while live data is changing and assume the resulting archive is consistent.

Create an appropriate storage-level snapshot operation using IndexedDB transactions.

Verify:

- Every recording refers to a valid exported note.
- Every exported audio blob has complete, correctly ordered chunks.
- Recording metadata and chunks represent a consistent snapshot.
- Archive, Trash and Restore lifecycle states are preserved.
- No note revisions are modified during export.
- No accidental recovery or mutation occurs as a side effect of backup.

For active `recording` or `paused` sessions, choose the conservative policy:

**Block Full Archive export with a clear message requesting that active recording sessions be stopped/finalized first.**

Do not silently include incomplete in-flight recording data as though it were complete.

Handle interrupted or failed recordings with saved chunks explicitly, preserving their status and indicating that playback may be partial.

Preserve existing recording locks, interruption recovery and deletion safeguards.

## 6. Memory safety

Recording archives may be large.

Do not concatenate all recordings into one giant Uint8Array or repeatedly convert audio to base64.

Use Blob-based or streaming construction where appropriate.

Remember:

- `crypto.subtle.digest()` is not a streaming hash API.
- Blob construction is not guaranteed zero-copy on every browser.
- Compression and archive libraries may allocate additional memory.

Select an approach with clear memory boundaries and document the tradeoffs.

At minimum benchmark export/import with synthetic data sizes appropriate to the machine, including 50 MB and 200 MB. Record duration, peak memory where measurable, and failures.

Keep benchmarks isolated from live user data.

Do not claim fixed-memory or zero-copy behavior without measurement.

## 7. Import verification — Zero mutation first

Before any database write:

1. Identify the archive version and supported format.
2. Parse with file-count, total-size and entry-size limits.
3. Reject duplicate or unsafe archive entry paths.
4. Verify all expected entries exist.
5. Check byte lengths.
6. Verify SHA-256 for every file.
7. Validate every note record, allowing supported preservation of future-schema read-only notes.
8. Validate every recording metadata record.
9. Validate recording-to-note relationships.
10. Validate chunk ordering, count and audio consistency.
11. Reject malformed, truncated, corrupted or unsupported archives.

Never begin an import transaction if verification fails.

Do not trust imported MIME types, filenames, path components or metadata without validation.

## 8. Restore semantics and collision safety

Preserve the existing two import modes:

**Skip**
- If any incoming note ID or recording ID conflicts, abort the entire import.
- No partial writes.

**Merge**
- Never overwrite existing notes or recordings.
- Preserve all existing note revisions and audio bytes.
- Import new notes and their associated recordings together.
- If an incoming note already exists, conservatively skip its associated recordings rather than attaching unfamiliar media to that existing note.
- Report exactly what was imported and skipped.

Implement one IndexedDB readwrite transaction spanning the relevant stores for the commit step, so a failed commit does not leave orphaned records/chunks.

Do all asynchronous archive parsing, hashing and validation BEFORE opening this transaction.

Inside the IndexedDB transaction, avoid arbitrary asynchronous operations that could allow the transaction to become inactive.

Never clear or replace the existing database as a restore strategy.

Handle QuotaExceededError and transaction aborts without losing existing data.

## 9. Legacy V1 compatibility

Existing `noteos.local-backup` version 1 JSON files MUST still import exactly as before.

Do not break `makeBackup` / `parseBackup` compatibility for existing users.

V1 remains explicitly notes-only.

Future-schema read-only preservation must continue to work.

Do not migrate or rewrite existing notes automatically.
